# 初期版・運用の提案

2026-11-17 時点の提案。ユーザーの目標や決定事項は [企画・要件](product.md)、[決定事項と検討事項](decisions.md) を参照。以下の機能分割、数値、技術や運用の方針は、ユーザーによる採用前の案である。

## 進め方

最初から公開に必要な安全・削除対応を含めつつ、日記を順番に渡し、飾って楽しめる体験を小さく実装する。開発途中の試作を少人数で試し、一般公開向けの初期版で基本機能を整える。アップデートの順番は試作結果と開発負荷を見て決める。

## 公開前の試作案

実機で以下の３つを確認する。仮データでの試作と一般公開用の本番データは分ける。

1. 友人を招待し、参加・順番を迷わず理解できるか。
2. スマートフォンでフォーム入力、写真や装飾の配置、手書きが楽しく操作できるか。
3. プレビューして渡し、次の人が読んで反応する流れが伝わるか。

## 一般公開向け初期版の提案：iOS（機能分割は未確定）

| --- | --- | --- |
| アカウント | メールと Apple でのサインインを候補にし、アプリ内でアカウント削除できるようにする | 複数の作成方法と削除手段を確保する。認証連携の仕様は別途設計 |
| 日記帳 | 複数作成、最大10人、有効期限24時間の招待、途中参加と過去ページ閲覧 | 基本の利用ルール |

| ページ作成 | ２形式を含むテンプレート、テキストを中心に写真５枚まで、基本の装飾、移動・拡大縮小・回転と重なり順の調整、補助的な手書き | 書いて飾る魅力を早期に試す。テンプレート内容はユーザーが調べるため保留。８種類は全体の目標 |

| 渡す・読む | プレビュー、編集不可の注釈、渡す操作、表紙一覧と紙をめくるような閲覧、ページを書いた本人による削除 | 最低限の受け渡しと閲覧 |
| 反応 | 固定の種類のリアクションとコメント。リアクションは本人が取り消し可能。コメントは編集不可、本人が削除可能 | 友人同士のやり取りを試す。固定の種類に絵文字を使うのは提案 |
| 通知 | 自分の番・ページ追加・コメントを通知し、種類ごとにオフにできる | 進行と会話を把握できる。その他の通知は後から拡張 |
| 退出・削除 | いつでも退出、退出者のページ・コメントとそのページに付いたコメント・リアクションの削除、アクセス停止、日記帳は全員同意で削除 | 決定済みのルールを公開前に守る。実装前に未決定の詳細を詰める |
| 保護・サポート | 認可、招待保護、暗号化、バックアップ、プライバシーポリシー、問い合わせ窓口、通報と運営者による対応の検討。参加者のブロック・退出・該当日記帳での投稿削除。審査基準の整合を要確認 | 非公開データを守り、公開後に問題へ対応する |

### コメント文字数の提案

**200文字程度**を初期値として提案する。短く気軽に反応でき、文章が足りるか試作でも検証しやすい。実際の最適値を示す調査結果ではなく、試作用の仮の数字。文字数の数え方は絵文字や結合文字も踏まえて実装時に決める。

### 今後のアップデート案

- テンプレートを８種類程度に増やす。背景、装飾、手書きのペンや編集操作を拡充する。
- 自由配置をさらに柔軟にする。初期版でも基本の自由配置は実現し、複雑な表現は試作を踏まえて追加する。
- 固定のリアクションに加え、端末の絵文字キーボードから幅広く選べる仕組みを検討する。採用も提供時期も未決定。iOS と Android では絵文字の見た目が異なる場合がある。
- 日付・書いた人による検索、通知の対象拡充、表示や操作の改善。
- Android アプリ、その後のパソコン版。順序や時期は未確定。

## プライバシー・運用の推奨案

### 招待とアクセス

- 招待リンクは十分に推測しにくいランダムな値とし、発行から24時間で失効させる。第三者への転送を前提とし、参加前に日記帳名と過去ページを読めることを明示し、既存参加者にも参加を知らせる。リンクを持つ第三者が参加し得る点は、参加承認を追加するかを含め未決定。
- 招待の無効化・再発行を用意する。使い切りにするか複数人で使うかは未決定。参加上限はサーバー側で同時アクセスにも耐えるよう確認する。
- 日記・写真・コメントへの全リクエストでサーバー側が参加資格を確認する。下書きは作成者本人に限定。写真の保存場所を公開せず、取得時も認可する。操作権限もサーバーで確認する。権限を既定で拒否し毎回確認する方針は [OWASP の認可ガイド](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html) を参照。

### データと削除

- 通信と保存データを暗号化し、鍵や管理者権限へのアクセスを制限する。これは運営者を含む誰も読めないことを意味しない。エンドツーエンド暗号化を採用するかは別途検討。
- 写真は OS の選択画面を使い、利用者が選んだ写真だけを受け取る設計を優先する。位置情報などのメタデータは保存する必要性を検討し、不要なら除去する。
- 退出やページ削除は実行前に対象と影響を示す。退出者のページとコメント、退出者のページに付いた他者のコメント・リアクションも消える点を明示する。日記帳は全員が同意するまで削除せず、削除実行前は各参加者が自分の同意を取り消せる。削除後は元に戻せないことを伝える。アカウント削除はアプリ内から開始できるようにする。Apple はアカウント作成を提供するアプリにアプリ内での削除を求めている：[Apple の案内](https://developer.apple.com/support/offering-account-deletion-in-your-app/)。
- バックアップは暗号化し、保存期間・アクセス権・復元手順を決め、復元を試験する。通常データから削除後もバックアップに一時的に残り得るため、削除完了までの扱い・期限と復元時に削除を再反映する方法を設計し、利用者に明示する。期間は未決定。
- 取得するデータを最小限にし、利用目的、保存・削除、委託先、問い合わせ先をプライバシーポリシーで説明する。適用法や配信地域に応じて内容を確認する。[個人情報保護委員会の案内](https://www.ppc.go.jp/news/careful_information/use_AP_provided_by_3rdparty/)も参照。

### 一般公開の安全対応

- 友人限定でも、日記・画像・コメントを利用者が投稿するため、Apple のユーザー生成コンテンツに関する審査条件を確認する。Apple のガイドラインには不適切な内容へのフィルタリング、通報、悪質な利用者のブロック、連絡先の公開が挙げられている：[App Review Guidelines 1.2](https://developer.apple.com/app-store/review/guidelines/)。
- 通報を受けて運営者が確認し、必要に応じアカウントを停止する案を検討する。通報だけで自動停止する仕様とはしない。利用者によるブロック時は、その日記帳から対象者を退出させ、その日記帳内の対象者のページ・コメント・リアクションを削除する。削除ページ上の他者のコメント・リアクションも削除する。他の日記帳は対象外。ブロック時の確認、解除・再参加、バックアップなどの詳細と審査適合性は未確認。

### 運用・技術の考え方

- 小規模な初期運用では、認証・データベース・非公開ファイル保存を提供するマネージドサービスを候補にする。バックアップはプランごとの提供内容を確認し、不足分は別途設計する。Flutter、Supabase、Firebase Cloud Messaging の構成案で進める方向だが、各機能で上記の認可と削除を実現できるか検証する。契約や詳細構成は未確定。
- 開発用と本番用を分ける。エラー・稼働状況・料金上限や予算アラートを監視し、日記の本文や写真をログに出さない。
- 問い合わせ先、障害時の連絡方法、対応担当、サービス終了時のデータの扱いを公開前に定める。実際の月額費用は利用量・構成が未定のため見積もれない。

## 実装前に解消したい点

- 全員同意による日記帳削除で、途中参加者の同意も得る。退出が発生したときや申請の期限をどうするかは未決定。
- 退出者が他のページに付けたリアクションや共有写真をどう扱うか。
- 後から保存した下書きを優先する場合の、上書きへの注意表示、保存順の判定とオフライン・復帰時の扱いをどうするか。
- バックアップの保持期間、写真の対象範囲、削除反映と復旧手順を公開前に決める。通知に日記本文やコメントを含めるかも判断する。

## 開発と公開の補足

- 無料での公開を目指す。Flutter で進め、その他の技術は [技術構成の提案](technology.md) を参照。
- パステルテーマ、テキスト主体の編集、表紙が並ぶ一覧、紙をめくる閲覧の詳細は [デザイン](design.md) を参照。
- 通報と運営者による対応を検討する方向。利用者によるブロックの基本ルールは決定済み。フィルタリング、通信の秘密との関係、Apple の基準との整合性は未確認。[法務・公開時の確認](legal-review.md) を参照。
